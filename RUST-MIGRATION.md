# Оценка перехода Figma MCP на Rust

Дата: 25 октября 2026. Статус: план сравнительных испытаний; Rust-реализации и новых измерений пока нет.

Цель — уменьшить время ответа и потребление оперативной памяти. Решение принимается отдельно для каждого участка по специальным тестам Rust vs Node.js. Полное переписывание заранее не считается необходимым. Этот документ задаёт требования и место для результатов, но не запускает реализацию.

Связанные документы: [требования проекта](TASK.md), [план сетевого пути](TODO-network-selection.md), [контракт сессии](docs/network-session.md), [хранилище](docs/network-store.md).

## Ключевые требования

1. Сохранить внешний MCP-контракт, идентичность снимка и selection, порядок узлов, фильтрацию скрытых веток, пагинацию, ограничения ответа, отмену, ошибки и явное обозначение неполноты/устаревания. Проверять эквивалентность результатов до сравнения скорости.
2. Суммарный пик дополнительной RAM — не более **500 000 000 байт**: MCP, декодер, индексы, буферы, дочерние процессы и дополнительная память расширения. Базовая память браузера/Figma и Kilo исключается. Лимит JS-кучи или отдельного Rust-процесса не доказывает соблюдение общего бюджета.
3. В долгоживущей памяти хранить только ограниченное выбранное поддерево; не накапливать индексы всего файла и предыдущих selection. Одна тяжёлая операция одновременно. Ограничить очереди, входные буферы и распаковку; определить освобождение ресурсов после отмены и ошибок.
4. Обрабатывать снимки частями, не собирать полный JSON/base64 и полную объектную модель без необходимости. Новые снимки и промежуточные данные хранить в `.cache/figma-network/`. Управление поколениями и очистка должны работать одинаково для обоих вариантов.
5. Rust должен поддерживать фактически принимаемые варианты динамической fig-wire/Kiwi-схемы. Нельзя ускорять тест ценой жёстко заданной схемы единственного дампа, пропуска нужных полей или отключения проверок повреждённых данных.
6. Сохранить работу с существующим браузером и правами View, без REST API, платного Dev Mode, WSL/Docker и отдельной постоянно работающей службы. Целевые платформы — macOS и Windows. Новые зависимости согласовываются до добавления, как предусмотрено планом сетевого пути.
7. Учитывать стоимость интеграции: запуск Rust-компонента, IPC/FFI, копирование, сериализацию результата, распространение бинарников и поддержку двух реализаций. При гибридном варианте передавать обратно выбранный результат, а не весь документ.
8. Не переносить DOM-автоматизацию или экспорт в Rust только ради языка: задержки UI и рендеринг Figma измерять отдельно. Изменение алгоритма, формата хранения и языка фиксировать как разные факторы.

## Общая методика сравнения

- Для каждого участка реализовать отдельный воспроизводимый benchmark с одинаковым контрактом входа/выхода. Предлагаемые ID тестов приведены ниже; пока они не реализованы.
- Сравнивать три варианта, где применимо: **N0 — текущий Node.js**, **N1 — Node.js с сопоставимыми архитектурными оптимизациями**, **R — Rust**. Разница N0/N1 показывает эффект алгоритма, N1/R — эффект реализации. Если N1 отсутствует, явно указать, что язык и архитектура не разделены.
- Использовать одни и те же фикстуры: малый, типичный и большой снимки; маленькая и большая selection; много текста/стилей; тяжёлые исключаемые blobs; глубокое дерево; повреждённые/обрезанные сообщения; отмена. Для синтетики фиксировать seed. Для реальных снимков сохранять локально SHA-256 и размеры; приватные данные и секреты не коммитить.
- Зафиксировать commit каждого варианта, версии Node/Rust и зависимостей, release-флаги Rust, ОС, архитектуру, CPU, RAM, параметры теста и команду. На разных машинах результаты вести раздельно.
- Разделять холодный процесс, прогретые запросы, подготовку индекса, выборку, полный ответ и простой. Новый процесс не означает холодный файловый кэш ОС: его состояние указывать отдельно, не называть прогретое чтение холодным диском.
- Начальный протокол: 30 независимых холодных запусков; 10 прогревочных и 100 измеряемых запросов для тёплого пути; 60 секунд простоя; 100 последовательных смен selection для проверки накопления памяти. Для дорогих UI-тестов допустимо меньше повторов с явным указанием числа и ограничений выводов. Публиковать median/p95 времени и все сырые измерения, а не лучший запуск.
- Для RAM записывать абсолютный RSS, максимум за фазу, максимум за весь сценарий и остаток после завершения/отмены через фиксированные 1 и 10 секунд. Для нескольких процессов измерять максимум их **одновременной суммы**, не складывать пики разных моментов. Worker-потоки не считать вторым процессом. Описывать частоту семплирования и возможность пропуска короткого пика.
- JS heap, external buffers и Rust allocator statistics использовать для диагностики; основной критерий памяти — суммарный RSS с отдельно измеренной дополнительной памятью расширения. Принудительный GC допускается только в отдельном диагностическом тесте, не в основном сравнении.
- Микротесты дополнять полным MCP-сценарием. Ускорение распаковки не считать ускорением пользовательского запроса без проверки всего пути.
- В таблицах `—` означает «не измерено», а не ноль. В ячейке времени записывать `median / p95`, для памяти — значение согласно строке. Влияние вычислять как `(N1 − R) / N1 × 100%`: положительное значение означает снижение времени/памяти. При сравнении с N0 вместо N1 подписывать базу явно; для нулевой базы процент не вычислять.

## Как заполняем и принимаем решение

1. Для выбранного участка фиксируем гипотезу, фикстуры и минимальный полезный выигрыш **до** просмотра результатов. Указываем абсолютную величину (мс/МиБ) и относительную (%), допустимую регрессию второй метрики. Универсальный процент для всех участков не задаём: экономия миллисекунды и сотни МиБ имеют разную ценность.
2. Готовим тест корректности и воспроизводимый benchmark, затем сопоставимые реализации. Время и память измеряем на release-сборках без профайлера; профилирование аллокаций — отдельная диагностическая серия.
3. Создаём локальный каталог `.cache/figma-network/benchmarks/rust-vs-node/<run-id>/` для сырых результатов и метаданных. Публичную обезличенную сводку сохраняем в `artifacts/rust-vs-node/`; перед коммитом исключаем содержимое макетов, секреты и приватные пути.
4. Для каждого набора данных и платформы добавляем отдельную копию таблицы с run-id; не перезаписываем прежние результаты и не смешиваем разные фикстуры в одной цифре.
5. Записываем итог в сводную таблицу: что улучшилось, что ухудшилось, достигнут ли заранее выбранный порог, какова стоимость поддержки и почему выбран перенос/отказ/отсрочка. Если разброс сопоставим с выигрышем, вывод — «нужны дополнительные измерения».
6. Принимаем перенос только после проверки корректности, бюджета RAM и полного сценария. Если выигрывает N1 без Rust, фиксируем это как достаточный результат оптимизации.

## Исторические ориентиры — не результаты Rust vs Node.js

- [Mock MCP](artifacts/resources-mock.json): около 26 МиБ idle RSS; маленькая фикстура, без реального Figma.
- [Контекст и переменные](artifacts/context-benchmark.json): локальная медиана преобразования 0,455 мс на 90 узлах; живой DOM-сценарий занимает десятки секунд.
- [DOM-обход](artifacts/speed-comparison.json): 128 уникальных узлов, около 24,2 с внутри обхода.
- В предыдущем исследовании сетевого пути сообщались около 117 МиБ JS heap после GC и 339 МиБ peak RSS, подготовка в MCP около 1,15 с и выборка около 3 мс. Эти цифры не включают расширение, не подтверждают общий лимит RAM и должны быть воспроизведены новым benchmark перед использованием как базы.

Приоритет первого исследования: R03/R04, затем R01/R02/R05; R07–R10 проверять по фактическому вкладу в полный сценарий. R06 имеет смысл исследовать вместе с потоковым входом и ограничением очередей.
