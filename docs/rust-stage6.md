# Этап 06: managed-вход и Zstandard

**Решение пользователя: этап 07 (R03, Kiwi-декодер) принят на Rust. Ранее принятые R01/R02 сохраняются; этап 08 развивает общий Rust-путь до индекса, обхода и selection-кэша. Это не решение о полном переписывании всей серверной части: контекст, MCP-обвязка и ассеты оцениваются на своих этапах.**

Проверка на macOS arm64, 25 октября 2026. Production `src/`, расширение и npm-зависимости
не менялись и совпадают с N0 `fc3aaea`. Это сравнительный прототип в `rust/helper`
и `scripts/rust-helper/stage6-*.mjs`. Этапы Kiwi, индекса и retained lifecycle здесь
не реализуются. Windows-приёмка остаётся этапом 15.

## Граница реализации

R01: Rust читает те же managed NDJSON-части, повторно читает manifest перед каждой
частью, проверяет snapshot, размер, SHA-256, тип файла, symlink/hardlink и identity
открытого файла на Unix. Лимиты: metadata 2 МиБ, часть 8 МиБ, 10000 частей,
суммарно 4 ГиБ, запись 24 МиБ + 4096, payload base64 24 МиБ. Проверяются sequence,
единственный socket, UTF-8, длина session/requestId в единицах UTF-16 и
канонический base64. На входе одновременно обрабатываются одна часть и одна
запись; вывод блокируется pipe backpressure. Содержимое частей не перекодировано
в новый формат. Каталог передаётся доверенной тестовой обвязкой, а не через MCP;
lease и координация NetworkStore остаются в Node.js.

R02: `frame.rs` проверяет единственный кадр, magic, flags, известный content size,
размер окна, типы/длины блоков, truncation и trailing bytes до выделения выходного
буфера. Затем zstd распаковывает в буфер ровно заявленного размера. Лимиты схемы
2 МиБ и сообщения 64 МиБ совпадают с production. Встроенный Zstandard 1.5.7,
без dictionary builder, legacy и многопоточности. CPU/RSS на Unix получаются
через `getrusage`; на Windows эти метрики пока неизвестны.

### Совместимость включает Node fallback

Голый native-декодер **не эквивалентен** fzstd на всех повреждённых блоках:
fzstd иногда принимает повреждённый блок, который libzstd отвергает. Содержимое
checksum fzstd также не проверяет. Для паритета используется явный
`ForceIgnoreChecksum`, а при native-ошибке `compatibleInflater` повторяет только
этот кадр существующим `inflateFrame`. Полученный результат либо ошибка остаются
результатом N0. Частичный native-результат не возвращается. Таймаут и отмена не
запускают fallback. В обычной серии реальные кадры проходят без fallback.

Аналогично serde_json отклоняет некоторые допустимые для JSON.parse формы:
BOM, lone escaped surrogate, глубокие неизвестные поля. `compatibleInput`
повторяет чтение через исходный Node reader. Уже выданные записи проверяются
потоковым SHA-256 с длинами и пропускаются; дубликаты не выдаются и весь снимок
не накапливается в RAM. Caller удерживает read lease до конца итерации.
При изменении уже выданного префикса replay завершается ошибкой.

Таким образом, совместимый кандидат — **Rust + сохранённый Node fallback**.
Самостоятельные native-режимы служат измерению обычного пути, не являются
самодостаточной production-заменой. Legacy probe остаётся отдельным Node reader;
тест проверяет те же сообщения и их распаковку через совместимую границу.

## Протокол прототипа stage6-v1

Исходный текстовый протокол helper v1 не изменён. Дополнительный CLI
`--stage6 MODE [CONFIG]` используется только стендом:

- `input-stream CONFIG`: ограниченный JSON config с directory/snapshot;
  stdout — повторяемые `length:u32le + bytes` бинарных сообщений.
- `inflate-stream`: stdin — `length:u32le + outputLimit:u32le + frame`;
  stdout — `length:u32le + inflatedBytes`. Один outstanding запрос.
- `input-bench` / `inflate-bench CONFIG`: JSON-отчёт времени, CPU работы и digest
  упорядоченной последовательности байтов. `inflate-bench` читает подготовленные
  кадры из `frames.bin`; этот файл не заменяет managed NDJSON.
- EOF завершает stream. Неверный пакет/файл завершает helper с кодом 1;
  stderr — диагностическая ошибка. Успешное завершение добавляет в stderr
  `STAGE6_METRICS` с CPU и kernel high-water RSS.

Node-хост ограничивает packet/log, прерывает subprocess по deadline/AbortSignal
и ждёт close. В stdout не выводятся диагностические логи. Способ не добавляет
постоянную службу и не требует запускать новый браузер.

## Воспроизводимость и методика

```sh
export CARGO_HOME="$PWD/.local/cargo"
export RUSTUP_HOME="$PWD/.local/rustup"
export PATH="$CARGO_HOME/bin:$PATH"
cargo test --locked --manifest-path rust/helper/Cargo.toml
cargo build --release --locked --manifest-path rust/helper/Cargo.toml
npm run check
npm test
node scripts/rust-helper/stage6-measure.mjs
```

Для полного измерения нужен локальный корпус `.cache/figma-network/rust-corpus-real/`.
Его hashes проверяются перед запуском. Два дополнительных набора создаются из
фиксированных synthetic fixtures: 1000 и 4097 узлов, raw Zstandard blocks.
Синтетика не доказывает скорость распаковки сжатых данных. Сохраняются исходные
15 границ частей реального снимка. Одна и та же страница служит входом для
малой/типичной selection; размер selection не меняет работу R01/R02.

Для каждого набора и участка: 30 отдельных cold-процессов на реализацию,
циклический порядок Node/Rust, плюс один warm-процесс с 10 прогревами и 100
измеряемыми проходами. Warm означает повторения в одном хосте; у input-hybrid
helper запускается заново на каждом проходе — retained компонент не подменяется
будущей архитектурой. Файловый OS cache не сбрасывается, принудительного GC нет.
N1 и альтернативный формат отдельно не реализованы: в таблицах N1 неприменим.

Время микростендов включает чтение файлов, проверки и общий length-prefixed
SHA-256 результата. CPU работы измеряется после загрузки конфигурации; CPU всего
процесса (включая startup) также сохраняется отдельно. Warm CPU относится к
пакету из 110 проходов, а не к одному измеряемому вызову. RSS standalone — kernel
high-water одного процесса; он **не заменяет** RSS гибрида.

Полный диагностический load/decode/index: 30 Node и 30 Node+Rust процессов;
меняется только распаковщик, сохранены schema/live decoder, Kiwi и индекс.
Время включает запуск helper, обе передачи байтов, finish и завершение helper.
Затем проверяется digest контекста всех узлов малой selection. Это не публичный
MCP `get_design_context` и не приёмка Kilo/браузера.

Observer каждые ~10 мс читает RSS PID хоста и известного helper. Суммируются
одновременные значения, не независимые high-water marks. Observer CPU и сырые
samples записаны отдельно. Sampling может пропустить короткие пики; standalone
high-water, sampled combined peak и неизвестные значения не смешиваются.
Пик всех входных буферов отдельно не измерен. Бюджет 500000000 байт для всего
продукта (включая расширение) этим стендом не принимается.

Пороги заданы этапом 04 до этих запусков: время минимум −20% (warm также ≥2 мс)
либо память −15%, регрессия другой метрики ≤5%; отдельный cold-компонент должен
давать ≥10% полного запроса. Неудачный standalone-перенос разрешено отклонить.

## Проверки и зависимости

Зависимости пользователь согласовал в этом чате. Прямые версии pinned,
транзитивные — Cargo.lock. libc уже входит через zstd-sys и используется напрямую
только для диагностических метрик. [Проверка полного lockfile по RustSec](rust-stage6-dependencies.json)
содержит revision базы и найденные исторические advisories: выбранные версии
base64, sha2, shlex входят в исправленные диапазоны. Это не полный аудит кода.

Тесты охватывают wire-корпус, split-record, Unicode/UTF-16, canonical base64,
точные границы payload/record/window, повреждения частей/manifest, symlink/hardlink,
truncation, дополнительные кадры, raw/RLE/пустой кадр/checksum, реальные compressed
frames и детерминированные мутации, JSON.parse fallback без повторов, legacy,
отмену, timeout, oversized packet, завершение PID. Приватный real-тест в CI
явно пропускается при отсутствии локального корпуса. macOS job расширен; новый
CI в этой сессии не запускался.

Предварительные smoke/диагностические серии не используются как итоговые данные.
Сырые данные сохраняются в `.cache/figma-network/stage6-benchmark-*/`; приватные
снимки, пути query и распакованные данные не добавляются в Git.

В R01 Rust-кандидат — Node-хост + subprocess с совместимым replay; в строках
R02 «набор кадров» — отдельный Rust-процесс, без существующего MCP-хоста.
Последние три строки — Node + Rust только вместо распаковщика. Ускорение
standalone-строк не приписывается всему продукту. Времена включают указанные
выше проверки/чтение/digest, а не только вызов libzstd.

- **R01 — принять Rust-чтение и развивать далее (решение пользователя).**
  Cold: 22.05 → 16.90 мс (−23.3%); это принято как достаточное основание
  сохранить Rust-reader основной реализацией для следующих этапов миграции.
  Warm: 12.01 → 11.02 мс (−8.2%, менее 2 мс); первоначальные warm-пороги
  и требование ≥10% полного cold-запроса для отдельного участка не выполнены.
  Пользователь осознанно принял R01 с этими ограничениями. Следующие этапы
  развивают общий Rust-путь вход → Kiwi → индекс; измерения не изменены.
  Native-only результат 6.92 мс по-прежнему не включает Node-хост и IPC.
- **R02 — принять Zstandard на Rust и развивать далее (решение пользователя).**
  Ускорение standalone-набора −80.5% принято как основание развивать Rust-
  распаковку вместе с R01, Kiwi и индексом. Полный load/decode/index улучшился
  только на 4.9%, меньше исходного порога 10%; медиана sampled combined peak
  выросла на 5.9%. Максимумы sampled peak по серии: 176.17 → 180.30 МиБ (+2.3%);
  это другая агрегация. Пользователь принял R02 с этими ограничениями.
  Следующие этапы развивают общий путь вход → Zstandard → Kiwi → индекс,
  чтобы распакованные байты оставались внутри Rust-компонента.
- **Production пока остаётся Node.js.** Rust-чтение и Zstandard приняты как
  реализации миграционного пути; их production-подключение выполняется после интеграции
  и приёмки по плану. Это не закрывает следующие этапы.

Самостоятельное review: проверены размер до allocation, отдельные процессы,
lease/replay без дублей, пределы UTF-16 и UTF-8, CRC/checksum-совместимость,
отсутствие GC/изменения входного формата, разделение CPU startup/work,
суммирование RSS по одновременным PID и сохранение неизвестных метрик.
`npm run check` успешно; `npm test` **311/311** (включая 10 новых stage6-тестов,
реальный приватный тест выполнен локально); Cargo test **2/2**.
Предварительный прогон лимитного теста обнаружил ошибку самой UTF-8-фикстуры;
после исправления полный прогон прошёл. Рабочее дерево не закоммичено.
