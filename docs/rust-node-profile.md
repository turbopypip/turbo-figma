# Профиль Node.js — этап 04

Протокол зафиксирован 25 октября 2026 до сравнений с Rust.
База N0: production src/extension/package.json/package-lock.json совпадает с
`fc3aaea64de4878cfa655072d5f5830d44829892`. Измерительные scripts дополнены,
production-код не меняется. Основной путь — публичный get_design_context через
stdio MCP и managed snapshot, полученный replay замороженных событий.

## Предварительные критерии пользы Rust

Пороги для последующих R01–R10 не подбираются по полученному Rust-результату:

- Основной путь: median целевого cold/warm/full-traversal времени лучше минимум
  на 20%, p95 не хуже более чем на 5%; для warm дополнительно минимум 2 мс
  абсолютного выигрыша. Для cold выигрыш отдельного участка должен дать минимум
  10% ускорения полного запроса, иначе перенос участка откладывается.
- Вариант ради памяти: минимум 15% снижения одновременно измеренного RSS
  host+Rust, при регрессии median/p95 времени не более 5%.
- Вариант ради скорости: рост одновременно измеренного RSS не более 5%.
  Полный бюджет дополнительной памяти 500000000 байт проверяется отдельно с
  расширением. Этот профиль его не принимает.
- Корректность, количество и порядок узлов, полнота, ошибки, лимиты и параметры
  остаются эквивалентными. Микроускорение без улучшения MCP не считается успехом.
- Архитектурное изменение (например, новая политика проверки hash или индекса)
  сначала сравнивается как N1 с N0; выигрыш не приписывается языку.

## Условия и воспроизводимость

Корпуса этапа 02 предварительно проверены по hashes: synthetic 19 cases/45 files,
real 3 cases/19 files. Реальные выборки — кнопка 5 узлов, секция 39, гигантская
страница 1167 (stress-only). Синтетика beyond-selection-cache — 4097 узлов.

Обнаружено: реальные golden-ответы содержат UI-kit matching с fingerprint
`0feef4b502d65252f735aa6bcbf6c8303841f23f45cff02de5d04ea5bd413537`.
В manifest этапа 02 путь UI-kit не указан. Для основных измерений его локальная
копия зафиксирована как `rust-corpus-real/profile-ui-kit.variables.scss`;
теперь путь передаётся явно через `--variables-file`. Без UI-kit число страниц
и объём ответа отличаются, поэтому результаты этих режимов не смешиваются.

Основная серия: 30 независимых процессов; 10 прогревочных + 100 измеряемых
повторов первой страницы; полный проход continuation до null после прогрева;
смена selection и возврат. Повтор первой страницы и повторная страница различаются
в отчёте. Короткий idle основных серий отделён от отдельной проверки 60 секунд
idle и release через 1/10 секунд. OS cache не сбрасывается, forced GC отсутствует.
Серии запускаются последовательно, без параллельных benchmark-процессов.

Фазовый диагностический profiler отдельно вызывает те же production-функции:
managed streaming/JSON, base64 validation, Zstandard, BoundedWireDecoder, disk
index, context query и JSON.stringify. Kiwi-время исключает callback acceptNode;
streaming включает readPart и его hash/manifest, их нельзя складывать.
Wrappers имеют накладные расходы, поэтому фазовые данные не заменяют MCP latency.

## Интерпретация профиля и очередность прототипов

Исходный код подтверждает два механизма, которые следует учитывать отдельно от языка:

1. Retained reader привязан к selection. Изменение nodeId меняет ключ и уничтожает
   предыдущий worker/index (`src/network-reader.ts`). Поэтому смена selection
   оплачивает декодирование всего снимка, а не только нового компонента.
2. `DiskNetworkSnapshot.query` продолжает обход после заполнения страницы:
   native variables, geometry, instances, children и итоговые счётчики вычисляются
   для всей доступной selection (`src/network-disk.ts`). Поэтому множество малых
   continuation-страниц может быть намного дороже одного первого ответа.

Кандидат N1 для дальнейшего отдельного исследования — переиспользование результатов
обхода/ограниченного индекса selection без изменения порядка, live-инвалидации,
completeness и memory limits. Это **архитектурная оптимизация Node.js**, а не
результат переноса на Rust. Второй кандидат N1 — устранить повторный разбор manifest
внутри проверки всех частей, сохранив проверку SHA-256 каждой части. Целостность
нельзя отключать ради более красивого warm-результата.

После каркаса этапа 05 приоритет измеряемой выгоды — Kiwi (07) и построение дискового
индекса (08). Этап 06 нужен как проверенная входная граница; самостоятельный перенос
только Zstandard оценивается по порогу полного запроса и не включается автоматически.
Этап 09 остаётся обязательной проверкой эквивалентности всего контекста; улучшение
многократного обхода/pagination оценивается отдельно как N1 и в интеграции этапа 10.
В этом этапе ни одна из этих оптимизаций не включалась в production.

### Гонка idle/release в измерительной обвязке

Первый 60-секундный idle-прогон (`pipeline-iw2jNMCrcqSZ`) завершился ошибкой
`Selection release failed` и не включён в успешную статистику. На границе TTL
сам reader уже запускает освобождение; второй вызов `releaseNetworkSelection`
при active/busy отклоняется. Конкурентное поведение воспроизводится отдельным
регрессионным тестом. В benchmark service ручной release/shutdown переведён на
существующий `stopNetworkSelection`, который дожидается активной операции.
Production reader не изменён; поведение кратких серий до TTL не меняется.
Исходный неуспешный отчёт сохранён, длительный прогон повторяется отдельно.

Kiwi и наполнение индекса занимают вместе около **87% суммы неперекрывающихся

Для целой страницы первичная context-query занимает 165.096 / 167.020 мс (3 процесса).
Повторный полный обход для каждой из 410 страниц объясняет наблюдаемые десятки
секунд; SHA-проверка — лишь часть этой стоимости. Однократный JSON.stringify не

при документе 4097 узлов. Диагностический повтор показывает cacheHit=true,

(36 частей); количество файлов и повторная валидация manifest важны наряду с
размером данных. Синтетический Zstandard содержит raw blocks: его малое время
распаковки не переносится на реальные сжатые данные.

## Длительный idle и освобождение

Успешный повтор: `pipeline-sKNkRVdGO5dj`. После 60 секунд начального простоя RSS MCP
36.4 МБ; в конце 60 секунд после запросов —
45.4 МБ; через 1 секунду после stop —
48.6 МБ; через 10 секунд —
42.2 МБ. Это один lifecycle-прогон, не
распределение памяти. На 60-секундной границе уже действует автоматический TTL,
поэтому последняя idle-точка не гарантирует наличие worker.

В коротких сериях остаточный RSS через 1 секунду значительно выше (например,
median 217 МБ для кнопки). Освобождение worker/index не обязывает V8/аллокатор/ОС
немедленно вернуть весь RSS. Принудительный GC не применялся. Проверены каталоги
всех успешных серий и фазовых запусков: decode scratch после завершения отсутствует.
Это не доказательство отсутствия любых утечек; длительная смена selection остаётся
отдельной проверкой этапа 10.
