# Ранний замер сетевого пути (TODO 07)

25 октября 2026. Это исходная точка для оптимизации, **не приёмка лимита 500 000 000 байт**.
Память самой вкладки Figma, её штатных worker, базового браузера и Kilo исключается по требованию пользователя.
Измеряются процесс MCP вместе с decoder worker и отдельный процесс нашего расширения.
В RSS расширения включён весь его процесс (в том числе popup); это консервативный учёт, без вычитания его простоя.
Добавочная нагрузка CDP в общих процессах Chrome пока отдельно не атрибутирована.

## Воспроизведение

```sh
npm run measure:network -- --synthetic
npm run measure:network -- --capture /absolute/path/probe.json --node-id 1:22975
npm run measure:network -- --capture /absolute/path/probe.json --node-id 1:22975 --live --extension-pids 12345
```

В live-режиме сначала определить PID **Figma Kilo Browser Bridge** в диспетчере задач Chrome.
Не подставлять PID вкладки Figma или сумму всех процессов Chrome. Service worker и popup одной группы могут иметь общий PID — считать его один раз.
Стенд пишет путь к приватному `pairing.txt`; подключить расширение к указанному localhost-порту и нажать «Перезагрузить и захватить» в нужной вкладке Figma.
На повторном запуске `--reuse-pairing /absolute/path/pairing.txt` сохраняет тот же ключ и порт; прежний стенд должен завершиться.
Если PID расширения изменился, измерение его памяти нужно повторить с новым PID. Проверить отсутствие пропусков PID в samples.
Смена вкладки во время работы UI-автоматизации мешает запуску, но сама по себе не входит во время захвата.

Каждый запуск изолирован в `.cache/figma-network/benchmarks/pipeline-*`: конфигурация, секрет, исходные события, рабочий кэш, преобразованный probe, `samples.ndjson`, `report.json`.
Эти файлы не публикуются в Git. В отчёте нет ключа подключения, URL файла и содержимого макета.
Старые дампы не перемещаются. Новых зависимостей нет. Настройки: `--interval-ms` (20), `--idle-ms` (1000), `--release-ms` (10000).

## Что именно измеряется

Supervisor создаёт отдельный MCP-процесс, запускает настоящий stdio MCP, bridge, инспектор начального потока и NetworkStore. Его собственные подготовительные аллокации не включаются.
В replay-режиме production collector работает в отдельном Node-процессе с моделью Chrome API: его RSS показан отдельно и **не считается памятью расширения**. Это также не измерение скорости реальной сети.
В live-режиме работает установленное расширение Chrome, настоящий CDP, localhost WebSocket и текущая Figma.

После публикации снимка измеряемый MCP-процесс читает проверенные части под read lease и преобразует NDJSON в probe JSON на диске. Этот **адаптер только для стенда** удерживает одну ограниченную запись, проверяет один поток и ограничение 64 МиБ; его время/RSS входят в отдельный этап `benchmark-probe-adapter`.
Оба запроса `get_network_tree` затем читают именно снимок этого запуска. Они не читают прежний входной дамп. Для live входной `--capture` используется только как seed конфигурации; `fixture.sha256` в сыром отчёте — хеш seed, а не свежего снимка. Хеш свежего probe сохранён в публичном baseline.
Этот адаптер использовался в baseline TODO 07. После TODO 08 текущий стенд передаёт `snapshot` в `get_network_tree` и читает части напрямую; адаптер остаётся только исследовательским helper. Новые результаты: [дисковый декодер](network-disk.md).

Этапы: запуск, простой, захват, адаптер, первый запрос, повторный запрос, освобождение через 1 секунду и ещё 10 секунд простоя.
В `live-setup-and-capture` входит ожидание пользователя; чистое время захвата — `captureDurationMs`, от begin до публикации ready. Метрики decoder worker отдельно показывают чтение JSON, decode, индекс и выборку.
«Холодный» означает первый запрос в свежем MCP-процессе, а не холодный файловый кэш ОС. Повторный запрос пока снова создаёт worker и декодирует документ. Принудительный GC не вызывается.

RSS снимается снаружи через `ps` (КиБ × 1024); Windows-ветка использует WorkingSet64, но на Windows здесь не проверялась.
Пик суммы — максимум **одновременных** отсчётов MCP и расширения, не сумма их независимых максимумов.
Worker разделяет RSS процесса MCP и не прибавляется второй раз. `heapUsed`, `external`, `arrayBuffers` — диагностические поля: arrayBuffers уже включён в external, оба уже входят в RSS. `maxRSS` — накопительный максимум с запуска процесса, не максимум отдельной фазы. См. [Node process memoryUsage/resourceUsage](https://nodejs.org/api/process.html).
Опрос не гарантирует обнаружение кратких пиков. Поэтому `fullImplementationPeakBytes=null`, `budgetAccepted=false`, даже когда наблюдаемая сумма меньше бюджета.

## Исправления и проверки

Живой Chrome выявил повторяющийся `loading` после `complete` при запуске worker. Собственный reload теперь допускает эти уведомления до окончания начального захвата; смена файла, закрытие потока/владеющей worker-сессии и общий дедлайн по-прежнему прерывают захват. Готовность определяется подтверждённым JOIN_END.
Измеритель больше не вызывает cache.info параллельно записи: такой опрос создавал `Cache BUSY`. Готовность берётся из результата commit.
Первые неуспешные прогоны сохранены в локальном кэше и не используются как baseline.

Self-review: проверены приватность отчёта, границы адаптера, освобождение worker, отсутствие двойного учёта RSS и влияние измерителя на запись. `npm run check`, `npm test` (145/145), `git diff --check` прошли.
Для окончательной приёмки нужны production decoder, серия запросов/крупные входы, контроль коротких пиков и атрибуция добавочной памяти CDP, а также Windows (TODO 20). Базовую память самой Figma оптимизировать не требуется.
