# Стенд Node.js / Rust — этап 03

Дата: 25 октября 2026. Стенд расширяет существующие `measure-network-pipeline.mjs`,
`measure-network-disk.mjs` и общий учёт RSS. Новых зависимостей нет.
Production-код не меняется. Rust подключается внешним драйвером после этапа 05;
отсутствующий драйвер приводит к явной ошибке, а не запуску Node под именем Rust.

## Запуск

Из корня репозитория (npm-команды предварительно собирают актуальный Node-код):

```sh
# Короткая проверка стенда, не профиль производительности
npm run measure:network -- --series 2 --synthetic --warmup 1 --warm-requests 3 --idle-ms 20 --release-ms 1000
npm run measure:network:disk -- --series 2 --nodes 1000 --name-bytes 128 --warmup 1 --warm-requests 3 --idle-ms 20 --release-ms 1000

# Протокол измерений для следующего этапа: 30 независимых процессов,
# в каждом cold, 10 прогревочных и 100 измеряемых warm-запросов
npm run measure:network -- --series 30 --capture .cache/figma-network/rust-corpus-real/probe.json --node-id 3215:21227 --warmup 10 --warm-requests 100 --idle-ms 60000 --release-ms 10000
```

`--series N` запускает каждый вариант N раз; без этого флага прежний одиночный
запуск сохранён. `--implementation node` выбирает текущий working tree.
Для выбора нескольких вариантов: `--implementation node,rust --drivers /absolute/drivers.json`.
Выбор реализации без `--series` подразумевает 30 запусков. Порядок вариантов
циклически сдвигается между повторами. Сценарии разных размеров запускаются отдельно:
компонент/секция не смешиваются со stress-only целой страницей.

Cold означает новый процесс и первый запрос, но не сброс файлового кэша ОС.
Warm означает повтор того же запроса в том же процессе с retained selection.
Никакого принудительного GC нет. Прогревочные запросы остаются в сырых данных,
но исключаются из сводных latency/CPU. Их память входит в пик всего процесса.
Legacy `disk --capture --url` сохраняется, однако каждый offline-запрос создаёт
worker заново: его фаза называется `repeat-offline-cold-request`, не warm.
Для managed cold/warm по замороженному probe используйте pipeline replay.

## Отчёт и учёт ресурсов

Выход — приватный каталог `.cache/figma-network/benchmarks/series-*/`:
`report.json`, `runs.json`, запрос и копия сырого отчёта для каждого варианта/повтора.
В `sourceReport` указан исходный каталог с полными RSS traces, включая
`samples.ndjson` pipeline. Не удаляйте его при переносе доказательного набора.

Сохраняются ОС/архитектура/CPU/RAM, Node, commit, dirty-флаг, SHA-256 production
исходников и package-lock. Working tree **не получает автоматически метку N0**:
перед заполнением таблиц нужно сверить его с базой `fc3aaea`. Запускайте через npm,
чтобы `dist` соответствовал исходникам. Для внешнего драйвера сохраняются его
версия, revision и build flags; их достоверность обеспечивает сам драйвер.

- По фазам: durationMs, cpuUserMs/cpuSystemMs, память до/после. CPU Node включает
  worker threads; их CPU и RSS повторно не суммируются. Rust child CPU будущий
  драйвер должен включать в агрегат явно, иначе оставлять неизвестным.
- Median для чётной выборки — среднее двух средних значений; p95 — nearest rank.
  Есть размер выборки, missing и max. Warm-запросы сгруппированы в сыром отчёте
  по процессам; объединённый p95 не означает независимость всех наблюдений.
- `sampledImplementationPeakBytes` — максимум одновременной суммы уникальных
  PID `mcp` и `implementation-*`. При пропущенном PID семпл не входит в сумму.
  `completeImplementationSamples` показывает число полных семплов. Пики разных
  процессов в разные моменты не складываются. Допустима только одна роль на PID.
- `extension-*` учитываются отдельно и в сумме с реализацией; simulator и observer
  исключены. Пустые измерения — null, не ноль. Итоговая приёмка 500 МБ остаётся false.
- Idle/retained/release: отдельные фазы, освобождение selection, RSS примерно через
  1 секунду и через заданный `release-ms` от освобождения (по умолчанию 10 секунд).
  Значения меньше секунды в старом pipeline CLI дают минимум 1 секунду.
- Наблюдатель работает вне измеряемого процесса. Его собственные CPU/RSS вынесены
  в `observer`: это **вся обвязка**, включая подготовку и orchestration, не чистая
  стоимость RSS-опроса. CPU краткоживущих ps/PowerShell не покрыт. Pipeline также
  сохраняет фактические окна/интервалы опроса. Семплирование может пропустить пик.

Ошибки серии сохраняются в runs.json, дают exit 1 и не становятся нулевыми
измерениями. Если упавший драйвер успел вернуть structured report, он копируется.
Драйвер имеет общий timeout 10 минут на запуск; disk child — 5 минут.
Эти пределы нужно учитывать для особо тяжёлых серий.

## Контракт внешнего драйвера v1

Пример локального drivers.json (пути и версии заменить фактическими):

```json
{
  "rust": {
    "command": "/absolute/path/to/benchmark-driver",
    "args": [],
    "version": "actual-version",
    "revision": "actual-commit",
    "buildFlags": ["--release"]
  }
}
```

Runner вызывает command без shell: `args + ["--benchmark-request", requestFile]`.
Запрос содержит `version:1`, `harness:"pipeline"|"disk"`, номер run, массив
`arguments` с теми же CLI-параметрами и modes (fresh-process, retained selection,
OS cache uncontrolled, forcedGc=false). Относительные пути разрешаются от корня
репозитория. Драйвер обязан реализовать эти режимы, завершать собственных потомков
при ошибке/отмене, писать служебные логи в stderr и вернуть в stdout единственный
JSON `{ "report": "/absolute/path/report.json" }`.

Формат отчёта совпадает с отчётом соответствующего Node-стенда: `success`,
`fixture.sha256`, `query`, `mode`, `warmup`, `warmRequests`, `stages`, `accounting`,
сырые фазовые и ресурсные измерения. Неизвестные метрики оставляются null.
Серия отклоняет отличающиеся hash/query/mode/warm-параметры. Синтетические генераторы
Node доступны в исходниках; внешний драйвер должен читать эквивалентные байты.
Для реального сравнения предпочтителен один сохранённый capture из корпуса.
Контракт проверен тестовым драйвером; это проверка протокола, не Rust-реализация.

Runner не доказывает функциональный паритет по одним счётчикам/хешам:
перед измерением кандидата обязательны differential-проверки по
[контракту корпуса](rust-comparison-corpus.md). Детальные R01–R10 измерители
подключаются по мере реализации следующих этапов; этот этап не создаёт Rust.

## Replay, live и границы проверки

Pipeline replay использует Node-симулятор сборщика; его RSS/CPU сохраняются отдельно
и не объявляются памятью расширения. `--live --extension-pids ...` сохраняет прежний
интерактивный захват; каждый новый процесс требует подключения расширения.
Live hash в отчёте относится к переданному reference probe, а не доказательству
идентичности вновь полученного живого снимка. Поэтому серия с несколькими
реализациями и `--live` отклоняется: сначала заморозьте одинаковый вход для replay.
Полная атрибуция дополнительной памяти расширения/CDP не доказана.

Проверка стенда на macOS: целевые тесты статистики, внешнего драйвера, несовпадающих
входов, RAM и настоящего cold/warm/release; короткая pipeline-серия из двух запусков.
Результат smoke-серии: `series-D1PC63dlIFWJ` (локальный приватный каталог).
Windows, живая Figma, Rust и профиль N0 в рамках этапа 03 не измерялись.
Полная серия, профиль CPU и пороги полезного ускорения относятся к этапу 04;
100 смен selection — к соответствующим интеграционным этапам.

Итоговые проверки: `npm run check` успешно, `npm test` — **294/294**,
`git diff --check` успешно.

## Профилирование публичного пути (этап 04)

Дополнительные параметры pipeline: `--public` выбирает публичный
`get_design_context`; `--all-pages` проходит continuation до null и проверяет
уникальность/число узлов; `--switch-node-id ID` измеряет смену selection и возврат;
`--variables-file FILE` явно подключает UI-kit. Для публичного пути `--depth`
по умолчанию 12 (как в корпусе), `--max-bytes` — 24000, maxNodes=200.
`--profile` включает счётчики host readPart: вызовы, байты, время чтения с проверкой
manifest/hash. Холодный worker читает отдельно, поэтому ноль host readPart на cold
не означает отсутствие чтений. `pageMeasurements` содержит размер и время каждой
страницы без текста макета и настоящего continuation.

`profile-stages.mjs PROBE NODE_ID RUNS [VARIABLES_FILE]` отдельно раскладывает
холодный managed decode по production-функциям. Это диагностический запуск с
таймерами, а не замена сквозного MCP. `summarize-profile.mjs PRIVATE_INDEX OUTPUT`
сводит ссылки на raw-отчёты из JSON `{label: absoluteReportPath}` в числовую сводку.
Результаты и ограничения — [профиль Node.js](rust-node-profile.md).
